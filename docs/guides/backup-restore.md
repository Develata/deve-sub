# Backup and Restore Guide

## Overview

Deve Sub provides `deve-sub backup` and `deve-sub restore` CLI subcommands for
full-state backup and restore. The backup captures the SQLite database,
non-secret configuration, and environment metadata in a versioned tar archive.

## Backup

### Creating a backup

```bash
deve-sub backup --output /path/to/backup.tar
```

Optional flags:

- `--config <path>` — configuration file (defaults to `DEVE_SUB_CONFIG` env or
  built-in search).
- `--db-path <path>` — database path (overrides config).

The backup runs while the server is online. SQLite `VACUUM INTO` produces a
consistent snapshot without holding a write lock.

### Generation-cache encryption upgrade

Schema 0029 adds encrypted generated subscription payloads. Stop `serve` and
run the explicit migration with the existing master key:

```bash
deve-sub migrate --db-path /path/to/deve-sub.db --key-path /path/to/master.key
```

The migration preserves historical cache identities and selections. Old output
remains unqualified for delivery until regenerated under current v7 semantics;
encryption alone does not prove that it preserved the original TLS policy.

Before an upgrade, the CLI checks migration history and key binding, then
creates a unique `.deve-sub-pre-migrate-*` private directory containing a
consistent `database.sqlite`, its hash manifest and matching loaded original
`master.key`. The default location is beside the database; `--rollback-dir`
selects another existing parent directory. These recovery files can contain
legacy plaintext and key material: keep their directory private (0700 and
files 0600 on Unix), separate from normal backup archives.

Schema and payload conversion run on a sibling staging copy. Missing/wrong
keys, backup I/O or conversion failure leave the live schema and business data
unchanged. Correct the cause and retry; completed rollback pairs are preserved.
An already-current, authenticated database is a read-only no-op. Populated
pre-0015 sensitive tables and unbound encrypted/HMAC state require separate
reviewed recovery. Pending plaintext caches prevent serving and normal backup.
No key is generated by migration. Management commands cannot implicitly upgrade
an existing old database. Stop the server and use the resolved database path
consistently for all commands.

Backups made after migration contain encrypted cache payloads. Restore requires
the matching key when cache entries exist, including when restoring a legacy
archive that needs backfill. Authentication and migration happen on staging
before replacement. An older binary cannot read schema 0029: rollback requires
the pre-upgrade archive and its matching key.

This does not erase old database pages, WAL files, copies or historical
archives. Short codes remain cleartext bearer credentials; backups still
contain usable secrets and require confidential handling. Encryption preserves
historical output bytes and does not revalidate their protocol semantics.
See [storage policy](../plan/13-storage.md) and
[protocol fidelity](../plan/05-protocol-engine.md#native-field-fidelity).

### Archive contents

| File | Description |
|---|---|
| `manifest.json` | Format version, schema version, timestamp, row counts |
| `database.sqlite` | VACUUM INTO snapshot of the SQLite database |
| `config.json` | Non-secret configuration (bind address, port, paths) |
| `metadata.json` | Binary version, git commit, host, OS |

### What the backup includes

The `database.sqlite` snapshot contains the **full production database**:
users, TOTP secrets, session tokens, subscription URLs, encrypted sensitive
fields, audit logs, traffic snapshots, probe data, and templates.

Treat backup archives as sensitive. Store them with restrictive permissions
and never distribute them off-box.

## Restore

### Restoring from a backup

```bash
# Stop the server first
deve-sub restore --input /path/to/backup.tar
```

Optional flags:

- `--config <path>` — configuration file.
- `--db-path <path>` — database path to restore into (overrides config).

### Restore behavior

The authoritative sequence is in [M11: Restore and migration](../plan/milestones/M11-archive-and-snapshot.md#restore-and-migration).
The CLI verifies key continuity and the archived row counts before applying
forward migrations to a staging database. It checks the manifest's schema
against the actual migration history, including checksums and success flags,
and checks any database key binding against the loaded key. It requires the
current schema and checks integrity before the atomic
replacement. A failed check leaves the existing database intact. Stop `serve`
first; the guard uses a sidecar flock, not the mere existence of WAL/SHM files.
Each restore uses a private, unique staging directory beside the target; a
previous crash's staging WAL/SHM cannot enter the restored snapshot. Normal
completion and errors clean up the current staging directory. Crash remnants
remain isolated for inspection and are not automatically deleted by retries.

### Restoring from an older schema

If the backup was created with an older schema version, `restore`
automatically runs forward migrations after copying the snapshot:

```bash
deve-sub restore --input /old-backup.tar
# Output:
#   Restore complete.
#   database: /var/lib/deve-sub/deve-sub.db
#   schema version: 13 -> 14
#   integrity: ok
```

## Scheduling

For automated backups, use cron or systemd timers:

```bash
# Daily backup at 03:00
0 3 * * * /usr/local/bin/deve-sub backup --output /backups/deve-sub-$(date +\%Y\%m\%d).tar
```

Retain old backups according to your recovery point objective. Back up the
master key separately and provide the matching key when restoring encrypted
data; the archive contains its reference/fingerprint, not the secret key.
When supplying `--key-path` or `DEVE_SUB_KEY_PATH`, backup and restore refuse a missing,
unreadable or invalid key. Backup preserves any existing output archive, and
restore preserves the target database. Check the
key path before retrying; omitting it is not a substitute for correcting it.
Backup also requires a matching key when the snapshot already has a database
key binding. An old archive without a binding remains unverified; matching a
manifest fingerprint alone does not prove all encrypted fields are readable.
A downgrade needs the pre-upgrade archive and the corresponding older binary.
Lifetime traffic projections remain in a backup after recent raw rows expire.

### 历史节点安全清单

升级含节点的 0030 以前数据库，需要显式 `--security-map`。清单必须是经复核的
JSON：`version: 1`、`reviewed: true`、原 `key_fingerprint`、
`expected_pool_revision` 和 `actions` 数组。每项包含原 `node_id`、
`expected_revision`、`expected_fingerprint`、`evidence_sha256` 和 `action`。
`quarantine` 仅隔离该旧 ID；确认无受影响节点时可明确提交空 actions。
先运行 `migrate --db-path ... --key-path ... --security-map ... --preview`。
预览列明最终隔离及链依赖 ID、解除安全隔离 ID，以及全局缓存重建影响。
实际应用使用同一条命令去掉 `--preview`，仍先保留匹配原 key 的私有回滚副本。
同一私有目录还保留已经解析并核验的清单及原输入字节，避免事后仅有哈希而缺原件。

`restore_tls` 只接受已隔离的旧 ID，并额外要求 `artifact`：原文件 `path`、
`sha256`、明确 `format` 和从 0 起的 `parsed_entry_index`。文件 SHA 必须等于
该项 `evidence_sha256`；只允许不改变其他 canonical identity 的 TLS 恢复。
输入不全、不支持、非 TLS 身份变化或身份冲突均保持隔离，等待单独复核。
修复不会创建新 ID，也不会替用户打开原本禁用的节点。

恢复历史归档时若含节点且尚无 0030 状态，restore 会拒绝隐式升级；先对归档的
隔离副本按上述清单迁移、验证并重新备份。不要更改历史迁移校验和或放宽 ledger
连续性来接受缺中间项的私有试验数据库。
